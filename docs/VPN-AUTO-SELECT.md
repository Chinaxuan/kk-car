# OpenVPN/TCP 与 WireGuard 自动选线

KK-Car 同时保持两条公司 VPN 隧道待命。物理上联从断线恢复或在有线 WAN、4G 之间切换后，选择器立即比较；平时每 5 分钟比较一次。每条隧道分别绑定 `ovpncar` 或 `wgcar`，依次检测公司内网 Ping、经该隧道的 HTTPS 加密 DNS，以及使用加密 DNS 返回地址访问 Google HTTPS。只有三项都通过，才允许参与延迟比较；探测包不会回落到物理 WAN。

每条隧道每轮发 5 个 Ping，至少收到 4 个，且加密 DNS 与国外 HTTPS 均成功，才视为健康；用公司 Ping 往返时间的中位数作为健康线路间的延迟，并对丢包加惩罚。只有候选线路比当前线路快 **至少 10 ms 且至少 15%**，连续两轮成立，并且距上次切换已满 10 分钟时才切换。网络恢复后的首次比较可直接选择明显更快的健康线路；当前线路不健康且另一条健康时立即切换。两条都不健康时保持当前选择，由防直连规则阻断经 VPN 的业务，不放行到物理 WAN。测得的低延迟只是当次路径表现，不保证移动途中每时每刻更快。

切换同时更新 PBR 的公司/国际业务与国外 DNS 策略、表 300 的隧道默认路由，以及 DNS 上游的接口绑定；选中线路必须再次通过真实路由、设备本地 DNS、国外 HTTPS 和三项端到端探测，否则回到原线路。平时还会检查 PBR、表 300、DNS 是否仍指向同一条隧道，发现漂移时尝试修复。旧线路保持在线，以便快速回切。两条隧道的管理地址分别有独立回程表，回复不会从另一条 VPN 或物理 WAN 发出。已有的 TCP 会话在切换时可能中断并重连；没有做多路聚合或零中断迁移。

「行车总览」和「连接设置」同时显示两条隧道最近一次探测的中位延迟、丢包和可用性，并标出当前实际业务线路、物理上联、策略路由与 DNS 是否同路由。每张卡还列出隧道地址、服务器与端口、传输协议、加密方式、MTU 和在线时长；服务器地址只由已登录设备实时返回，公开源码不保存。探测超过 10 分钟会标为过期，不把旧的低延迟当作当前可用。每 10 秒的实时延迟和历史曲线只记录**当前选中的 VPN**，不能代替两条线路的独立探测。网页的“暂停 VPN”会停止两条隧道并暂停选择器；“启动 VPN”恢复两条。开机自动连接开关同时控制 OpenVPN、WireGuard 和选择器的开机状态。网络守护按当前选中的协议执行恢复操作。

## 部署与恢复

这套逻辑针对现有 `ovpncar`、`wgcar`、PBR、DNS 与防火墙配置。新设备不可直接覆盖配置。部署前备份 `/etc/config/{pbr,dhcp,network,firewall}` 和原脚本，并验证两条隧道单独绑定接口时都能到达公司探测服务及所需国际出口。PBR 需同时支持 `ovpncar`、`wgcar`，WireGuard 不得在 ignored list；两条隧道需处于相应防火墙区并允许 LAN 转发。

服务为 `/etc/init.d/kk-car-vpn-select`，选择状态仅存 `/tmp/kk-car-vpn-select.json`。若需临时回到已验证的 OpenVPN 路线，先停用选择器，再将 `pbr.kk_global.interface` 和 `pbr.kk_dns.interface` 改回 `ovpncar`，恢复国外 DNS 的 `@ovpncar` 绑定，重启 PBR 与 dnsmasq，并运行 `/etc/kk-car/ike-route-ensure.sh`。核对表 300 默认路由为 `ovpncar`、不可达兜底仍存在，并从 LAN 客户端复测公司、国内和国外地址。不要只停用 `wgcar` 而保留指向它的 PBR 与 DNS 配置。

## 本轮验证边界

2026-10-07 初次部署时，两条隧道均能访问公司探测地址，WireGuard 曾通过国外 HTTPS 测试；但当天稍后国外访问失败。复查发现 WireGuard 仍能 Ping 公司地址，却无法通过固定地址访问 Google 或经 HTTPS 查询国外 DNS；OpenVPN/TCP 两项均成功。原选择器仅凭公司 Ping 判定健康，错误选中了 WireGuard。修复后，当前 4G 上 OpenVPN/TCP 的公司 Ping、加密 DNS 和 Google HTTPS 检查通过，WireGuard 因加密 DNS 不通被排除；PBR 两项、DNS 上游和表 300 均读回 `ovpncar`，本地 Google/ChatGPT 解析恢复。回归测试覆盖“公司 Ping 成功但国外出口失败”的误判。**尚未通过真实断开上联、移动中长时间运行或有线 WAN 重测**，因此不能承诺无感切换或始终选择绝对最低延迟。

2026-10-08 从设备当前 VPN 管理入口回读：当前业务线路 `ovpncar`、DNS 接口 `ovpncar`、表 300 就绪，两个隧道接口都已连接。最近一轮 OpenVPN 的公司探测、加密 DNS 与国外 HTTPS 通过；WireGuard 虽能到公司探测地址，但加密 DNS 未通过，因此保持备用而不切换。状态接口与页面改动没有修改运行中的分流配置或 VPN 密钥。浏览器登录后的视觉验收见 [验证记录](VALIDATION.md)。
